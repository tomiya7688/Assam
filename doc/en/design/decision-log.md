# Design Decision Log

Language: [日本語](../../jp/設計/決定ログ.md) | English

Decisions are collected in one place so that implementers do not reinterpret the design and cause rework. When a judgment is needed during implementation, read this first. Do not implement anything that contradicts it. If a contradiction is necessary, submit a **design PR that fixes this document first** ([workflow](../workflow.md)).

Categories:

- **Confirmed**: stated explicitly in an Issue or decided by the user. Changing it requires agreement on the Issue.
- **Proposed**: parts the Issue does not specify, decided by this design. Implementation may follow them. If review overturns one, update it in a design PR.
- **Open**: not yet decided. Work units concerned must decide before starting. If the "Blocks" column is non-empty, that work unit waits on the decision.

## Proposed (decided by this design)

| ID     | Proposal                                                                                                                                                                                                                                                                                               | Reason                                                                                                                                                               |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PRO-01 | profile identifier: name `core`, version `1`. The current `draft` is deprecated when `1` is fully implemented, and is managed as a version line separate from Full                                                                                                                                     | #3 "separate semantics by Core profile version"                                                                                                                      |
| PRO-02 | Core v1 ALU instructions take register operands only. Immediates are loaded with `const` (`add rd, rs1, rs2`). Only load/store have a signed offset immediate                                                                                                                                          | Matches the issue examples (`const` and `sub r1, r1, r2`). Reduces operand kinds in mapping tables and confines target-side immediate limits to `const` in one place |
| PRO-03 | Signed `MIN / -1` is `MIN` (wraparound), remainder is `0`, no trap. Divisor 0 is a `div_by_zero` trap                                                                                                                                                                                                  | Matches RISC-V default behavior; other targets are compensated in the mapping table. Satisfies the "specify the result" requirement                                  |
| PRO-04 | The opcode table is the list in [Core semantics](core-semantics.md)                                                                                                                                                                                                                                    | The minimal set that satisfies #3's required areas with neither excess nor shortfall                                                                                 |
| PRO-05 | Instruction index is 0-based. The value `jal` writes is "the index of the next instruction". If the `jr` target is outside `[0, instruction count)` (including one past the end), it is an `invalid_jump_target` trap. No implicit halt past the end of the instruction sequence                       | Fail-closed. Statically known out-of-range labels are rejected at load time                                                                                          |
| PRO-06 | Trap classification is a fixed enumeration (`div_by_zero` / `memory_out_of_range` / `invalid_jump_target` / `unknown_helper` / `explicit`). `explicit` carries a 32-bit unsigned user code. The step limit is an environment limit, separate from traps                                                | #3 "stable trap classification and location". Clarifies the bridge to the Python VM's current `VMError`                                                              |
| PRO-07 | The observable form of an execution result is common JSON: `{status: halted\|trapped, trap?: {kind, code?, pc}, registers[32], memory(sha256 or diff)}`                                                                                                                                                | Needed for comparing multiple VMs (conformance)                                                                                                                      |
| PRO-08 | Memory is given by the execution-instance parameter `memory_bytes` (default 1 MiB) and is a zero-initialized contiguous region. Sparse memory with unwritten read=0 is kept for Full only                                                                                                              | Resolves #3 "sparse memory's unwritten read=0 conflicts with the contract"                                                                                           |
| PRO-09 | The initial memory contents of a Core v1 program are given by the JSON IR's `memory.segments` (`{offset, bytes}`). Canonical text has no data directive (initialization is possible with `const` + `st*`)                                                                                              | Provisional for Q2. Does not grow the text grammar; extend under Q2 if needed                                                                                        |
| PRO-10 | Mapping table schema v2 declaratively holds conditions, width variants, scratch, and ABI helpers ([Target translation](target-translation.md))                                                                                                                                                         | #4                                                                                                                                                                   |
| PRO-11 | The conformance corpus is placed in `examples/conformance/` as JSON cases + expected observed results, and all VMs and translation results read the same files                                                                                                                                         | #8, #13, #14, #15                                                                                                                                                    |
| PRO-12 | Implementation is split into the work units WP-xx of the [implementation plan](implementation-plan.md), and proceeds as 1 work unit = 1 PR = 1 feature                                                                                                                                                 | Prevents rework                                                                                                                                                      |
| PRO-13 | Each instruction runs "decide traps, then commit side effects". `st*` checks the whole range first and never partially writes. An unregistered `hcall` id traps with no side effects. The instruction count written by a `jal` in the last instruction is an invalid index and traps if used with `jr` | Review feedback (Luna, Antigravity). Prevents observable differences between implementations                                                                         |
| PRO-14 | Out-of-range or overlapping `memory.segments` are rejected before execution with `core.load.*` diagnostics. Stack region, SP, calling convention, and register-preservation rules are outside Core (the Bitlang backend's responsibility)                                                              | Same. Keeps Core small (the principle of DEC-14)                                                                                                                     |
| PRO-15 | The quotient of `divs` rounds toward zero, and `rems = a - divs(a,b)*b` (the remainder has the sign of the dividend). Immediate ranges are fixed per instruction (`const` is `[-2^63, 2^64-1]`, etc.)                                                                                                  | Same. Needed for identical results on the three targets                                                                                                              |
| PRO-16 | v1 Core includes 64-bit high multiplication `mulhu`/`mulhs` (formerly Q1; 2026-11-07, recommendation adopted) | Without them, x\* multiplication becomes a runtime helper with remainder splitting, increasing the burden on the Bitlang side. On all three targets the multiply itself maps to 1-2 instructions (on x86 the whole translated sequence is longer once saving and restoring `rax`/`rdx` is included). Override via a design PR |
