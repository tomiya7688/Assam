## 2. Signing and Attestation of Release Artifacts (WP-A3)

- The `release` workflow is triggered by tags (`v*`) and is keyless via **GitHub Actions + OIDC**. Private keys, PFX, and keystores are not used and not committed.
- Steps: build (wheel/sdist) -> generate `SHA256SUMS` -> attest each with `actions/attest-build-provenance` -> attest `SHA256SUMS` itself too -> attach to the Release assets.
- Put verification into the CI/release gate: immediately before release, verify the freshly generated artifacts with `gh attestation verify` (or cosign), and do not release if it fails.
- Write user-facing verification steps in the README and Release notes:
  ```text
  gh attestation verify assam-X.Y.Z-py3-none-any.whl --repo tomiya7688/Assam
  gh attestation verify assam-X.Y.Z.tar.gz --repo tomiya7688/Assam
  gh attestation verify assam-conformance-X.Y.Z.tar.gz --repo tomiya7688/Assam
  gh attestation verify SHA256SUMS --repo tomiya7688/Assam
  sha256sum -c SHA256SUMS
  ```
- When publishing to PyPI etc., use Trusted Publisher (OIDC) and PEP 740 attestation (a separate WP when the decision to publish is made).
- Existing artifacts: no released artifacts exist at present (record this with `gh release list` at the start of A3). If any old artifacts cannot be reproduced, mark them "unsigned / unverifiable".

Completion criteria: enumeration of artifact types, digest + attestation for each artifact, successful verification in CI, no secrets in the repository, documented verification steps, and confirmation of the status of existing artifacts (#29).

## 3. Python Certificate Incident Response (WP-A1, #28)

Requirements (#28): `pip >= 26.2.2`, `certifi >= 2026.10.19`, and, if used, `uv >= 0.13.4` and `sigstore >= 4.5.1`. Do not treat the update command alone as completion; verify the **CA bundle actually trusted**.

Assam's investigation targets and policy:

| Target                                                      | Policy                                                                                                                                                                         |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CI (GitHub Actions)                                         | Bootstrap pip with a SHA-256-pinned wheel (introduced). A step that inspects pip's bundled CA bundle (introduced, `tools/check_pip_ca_bundle.py`). Record the result in the PR |
| Developers' local venvs                                     | Put verification commands in the procedure document, and record `python -m pip --version`, `certifi.__version__`, and `certifi.where()`                                        |
| Dependency declarations                                     | No stale pins in the `dev` extra of `pyproject.toml`. `uv`/`sigstore` are **currently unused** (pin minimum requirements when introduced for #29)                              |
| CA bundle inside distributed artifacts                      | The wheel is pure Python and does not bundle certifi. Record the confirmation result                                                                                           |
| Confirming the problematic certificate chain is not trusted | Per Issue #28, confirm by script that the chain in question fails verification against the actual CA bundle (extend `tools/check_pip_ca_bundle.py`)                            |

The confirmation record must include the Python/venv/artifact checked, the CA bundle or trust store referenced, and the versions at the time of checking. This work is proceeding on a separate branch (`fix/issue-28-*`); this design only organizes its completion criteria and does not start duplicate work.
