# ASSAM 開発ワークフロー

言語: 日本語 | [English](../../en/workflow.md)

この文書は、一回分の作業を完了させる手順を定義する。

## 1. 作業開始

- `doc/jp/開発予定.md` と関連仕様を確認し、対象を一機能に限定する。
- `git status` で既存変更を確認し、無関係な変更を保持する。
- 作業開始前に必ずリモートの変更を取り込む。

```text
git fetch origin
git pull --rebase origin <現在のブランチ>
```

競合が発生した場合は解決してからテストを再実行し、取り込みに失敗した場合は実装を開始しない。

## 2. 実装と検証

- 既存APIとテストを確認して実装する。
- 今回の機能に対応するテストを追加する。
- 開発用ツールはリポジトリルートで `python -m pip install -e ".[dev]"` により導入する。変更したPythonファイルだけを `python -m ruff format <ファイル...>` で整形し、`python -m ruff format --check <ファイル...>` で確認する（Ruff 0.15.22）。既存ファイル全体や他者の未コミット変更を一括整形しない。CIもPR／pushで変更されたPythonファイルだけを確認する。
- CIは依存関係の取得前に、[Pythonのセキュリティ告知](https://discuss.python.org/t/information-for-python-users-regarding-emudhra-emsign-ca-certificate-security-incident/109576/)に掲載されたSHA-256付きpip 26.2.2を導入する。これはCIのpip更新であり、既存の開発環境やOSの信頼ストアを検証したことにはならない（Issue #28）。
- CIはpip同梱のcertifi証明書束を実際に読み込み、emSign ECC Root CA - G3、またはクロス署名経路の起点となるAAA Certificate Servicesのいずれかが含まれる場合に失敗する。AAAの存在だけで脆弱性を断定せず、追加の経路検証が必要とする保守的な判定である。この検査はOSの信頼ストアやその他の証明書チェーンの安全性を確認しない。
- YAML・Markdownの変更にはNode.jsと `npm --prefix tools/format ci` で固定版Prettierを準備し、`npm --prefix tools/format run format -- <ファイル...>`、`npm --prefix tools/format run check -- <ファイル...>` を使う。パスは `tools/format` からの相対パスで指定する（例: `../../.github/workflows/ci.yml`）。
- 関連テスト、CLI、VM、JSON、端末通信を必要に応じて検証する。
- ターゲット網羅manifest・対応表を扱う作業だけ、[ターゲット対応表スキル](../../../.agents/skills/assam-target-mappings/SKILL.md) の対象別検証を行う。構造チェックと実行・意味の検証は区別する。
- 未検証の項目を完了扱いにしない。

## 3. 記録と完了

- README・仕様書・開発予定を必要に応じて更新する。
- 今回の作業内容、検証結果、未解決事項、次回対象を記録する。
- 差分を確認し、機能単位でコミットする。

## 4. PR・CI・セルフレビュー・マージ

Claude Code・Codex・ChatGPT・Copilot・人間の全員が同じ手順に従う。`main` へ直接コミットせず、`feat/`・`fix/`・`docs/`・`chore/` のブランチで作業する。

1. 再度 `git fetch origin` と `git pull --rebase origin main` を実行し、競合を解決してテストを再実行する。
2. ブランチをプッシュし、`.github/pull_request_template.md` を埋めて PR を作成する（`gh pr create`）。
3. CI（`.github/workflows/ci.yml`）の完了を待ち、`gh pr checks` で結果を確認する。短い間隔で繰り返し確認しない。
4. PR 全体の差分（`gh pr diff`）を [コーディングルール](../コーディングルール.md) に照らしてセルフレビューする。観点は、スコープ（1機能）、テスト、日英の文書更新、無関係な変更や他の貢献者の変更の混入、未検証事項の完了扱い。結果を PR の Self-review 欄に記録する。
   コード変更では、CodeRabbit の無料レビュー枠が使える場合にレビューを依頼し、枠切れまたは利用不可なら省略する。
5. CI が失敗した、またはレビューで問題が見つかった場合は、ブランチ上で修正してプッシュし、手順3からやり直す。
6. CI が成功し、セルフレビューで問題がない場合のみ `gh pr merge --squash --delete-branch` でマージする。そうでなければ PR を開いたまま理由を報告する。
7. マージ後に `git switch main` と `git pull --rebase origin main` を実行する。

一回分の完了条件は、リモート変更の取り込み、実装、テスト、必要な文書更新、CI が成功した PR のマージ、未完了事項の記録がすべて完了していることである。
