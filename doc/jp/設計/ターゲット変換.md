# ターゲット変換

言語: 日本語 | [English](../../en/design/target-translation.md)

対象Issue: #4（x64/ARM64/RISC-V）、#5（Wasm）、#6（JVM）、#2（mapping gate）。決定: DEC-12, DEC-13, DEC-15, PRO-10。

## 1. 責務の分離

```text
Core program (IR)
   -> [loader]        mapping JSON（versioned）を読み込み、registryと照合
   -> [expander]      Core命令 -> ターゲット命令テンプレート列（記号的）
   -> [allocator]     scratch / ターゲットレジスタの割当て（宣言された範囲）
   -> [encoder境界]   記号的命令 -> 機械語/アセンブリ文字列（ターゲット固有、別責務）
   -> [linker/ABI]    label・relocation・helper symbol（ターゲット固有、別責務）
```

- loader/expanderは**ターゲット非依存**で、対応表の宣言だけに従う。ターゲット固有コードは encoder 境界とABI adapterに閉じ込める。
- 対応表に汎用プログラミング言語を埋め込まない。複雑な意味低下が要るならCoreを分解する（#4）。
- 変換器はBitlang Lowのソースレベル意味（ownership等）を再構築しない。

## 2. 対応表 schema v2（PRO-10）

現行v1は命令列（opcode・operand参照）の形だけを持つ。v2で、意味に影響する情報を宣言的に追加する。

```jsonc
{
  "schema_version": 2,
  "core_profile": { "name": "core", "version": "1" },
  "registry_schema_version": 3,
  "target": { "architecture": "riscv64", "profile": "rv64gc" },
  "resources": {
    "scratch": ["t0", "t1"], // 変換で自由に使えるターゲットレジスタ
    "reserved": ["sp", "gp", "tp"], // Coreレジスタ割当てに使わない
    "register_map": { "r1": "x10", "r2": "x11" }, // Core r1..r31 -> ターゲットレジスタ（r0は定数0）
  },
  "mappings": [
    {
      "target_mapping_id": "assam.core.1.add",
      "variants": [
        {
          "when": {},
          "sequence": [
            {
              "opcode": "add",
              "operands": [
                { "kind": "core_reg", "index": 0 },
                { "kind": "core_reg", "index": 1 },
                { "kind": "core_reg", "index": 2 },
              ],
            },
          ],
        },
      ],
    },
    {
      "target_mapping_id": "assam.core.1.divs",
      "variants": [
        {
          "when": {},
          "sequence": [
            /* MIN/-1と除数0を明示した列、または abi_helper */
          ],
        },
      ],
    },
  ],
}
```

追加される表現（v1に無いもの）:

| 表現                                               | 目的                                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `register_map` / `reserved` / `scratch`            | Core r0〜r31のターゲットレジスタへの割当てと一時資源。r0はゼロレジスタに固定、または定数0に展開 |
| operand参照 `core_reg` / `core_imm` / `core_label` | Core operandのkindを区別（現行`core_operand`は位置のみ）                                        |
| `condition`                                        | 分岐条件のターゲット条件コード/命令へのmap（`eq`,`ne`,`lt`,`ge`,`ltu`,`geu`）                   |
| `variants[].when`                                  | 即値範囲やoperand同一性（`rd==rs1`など）による場合分け。条件は宣言的な比較だけ（範囲・等値）    |
| `abi_helper`                                       | ターゲットABIのhelper symbol呼出し（`assam_helper_<id>`、trap報告helper）                       |
| `trap_sequence`                                    | Coreのtrap（div_by_zero等）をターゲットでどう表すか（trap helperへ分岐する列を宣言）            |
| `unsupported`                                      | 事前のCore分解が必要な組合せの明示                                                              |

制約: `when`は有限個の述語（`imm_fits_signed(bits)`、`same_register(a,b)`等）のみ。ループ・再帰・変数を入れない。述語の集合はschemaで固定し、追加は設計PR。

## 3. Core admission gate（#4）

通常（`ordinary`）のCore opcodeを追加・変更するPRは、同じPRで次を満たす。

1. x64のmapping、2. ARM64のmapping、3. RISC-Vのmapping、4. mapping schema検証、5. 代表translation fixture（golden）。

`abi_primitive`（例: `hcall`）は、分類とhelper/ABI mappingを必須とする例外（DEC-12）。CIは「どのopcodeが三つのtableに網羅されているか」を機械検証し、未網羅の通常opcodeがあれば失敗させる（現行のcoverage manifest/matrix検査を、v1命令・v2表で再構成する）。

## 4. 検査の階層（意味の主張範囲を明確にする）

| 階層        | 内容                                                                         | 現状                | WP         |
| ----------- | ---------------------------------------------------------------------------- | ------------------- | ---------- |
| L1 構造     | schema・registry参照・重複・operand範囲                                      | 実装済み（Draft表） | 継続       |
| L2 網羅     | 三ターゲットの`in_scope`/`out_of_scope`宣言と表の一致                        | 実装済み            | C3で再構成 |
| L3 golden   | 代表Core programの展開結果（記号的命令列）が期待と一致                       | 未                  | C2/C3      |
| L4 実行等価 | 変換結果をターゲット上（またはエミュレータ）で実行し、参照VMの観測結果と一致 | 未                  | C4         |

CI/PR報告では**検査の階層名**を明記する。L1〜L2の成功を「変換が正しい」と書かない。L4は実行環境が必要で、利用不可なら環境を明示して未実施と報告する。

### L4の実行環境

- RISC-V: `qemu-riscv64` (user mode)。x64: ネイティブまたはqemu。ARM64: `qemu-aarch64`。
- CI（GitHub Actions）では、対応アーキテクチャのrunner/qemuが使える範囲で実行する。使えない場合は**ジョブをskipしてskip理由を記録**し、完了条件に「L4未達」と書く。
- 実行等価の比較対象は観測JSON（レジスタ・メモリ・trap）。ターゲットでtrapを観測する手段（trap helper、シグナル）はABI adapterの仕様として`trap_sequence`で定める。

## 5. 同梱対応表の移行

`examples/targets/`のDraft表（x86-64 / AArch64 / RV64I、`*-draft`）は、`core`版`1`の表へ置き換える。移行中は旧表をCIで並行して構造検査してよいが、v1の網羅が揃った時点で旧表を削除する。表のファイル名は`<arch>-<profile>-v1.{mapping,coverage}.json`とする。

現行のDraft表が`out_of_scope`にしている命令（除算・シフト・メモリ等）は、v1では`variants`/`trap_sequence`/`abi_helper`で`in_scope`にすることを目標とする。ターゲット固有の難所（既知）:

| 命令              | 難所                                                            | 方針                                                                                                 |
| ----------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `divs`/`rems`     | x86 `idiv`は`MIN/-1`で#DE、除数0でも#DE。ARM64 `sdiv`は除数0で0 | 前置の比較・分岐を`variants`で宣言し、PRO-03の結果を再現                                             |
| `shl`/`shr`/`sar` | シフト量がcl固定（x86）。マスク幅の違い                         | 6bitマスクを明示的に`and`、またはBMI2 `shlx`を`profile`で選択                                        |
| `mulhu`/`mulhs`   | x86は`mul`/`imul`がrdx:rax固定                                  | scratchでrax/rdxを退避する列を宣言                                                                   |
| `ld*`/`st*`       | 範囲検査（メモリ境界）                                          | ターゲットのメモリモデルと`memory_bytes`のbase+limit検査を列として宣言                               |
| `jal`/`jr`        | index値をレジスタへ入れる                                       | 命令indexをジャンプテーブルまたはラベル相対アドレス化するABI規則を定義（`jr`はindex→アドレス表引き） |

`jal`/`jr`の「命令index=レジスタ値」は、ネイティブでは**index→アドレス表**で表す。この表の生成はlinker/ABI adapterの責務で、対応表には「表引き」命令列だけを置く。

## 6. 独自 / FPGAターゲット（DEC-13）

- 開発者が`<arch>-<profile>-v1.mapping.json`を書き、`assam translate --mapping my.json prog.s`のように汎用translatorへ渡す。Assam本体の変更は不要。
- Core意味論は不変。表が対応しないCore命令は**明示診断**（`unsupported`宣言の有無にかかわらず、未対応は黙って近似しない）。
- 第一者CI（三ターゲット必須）の対象外。公式に昇格する場合は、専用のL3/L4 fixtureとCIを追加する。
- `docs`に「独自ターゲット表の書き方」の最小例（FPGA向けの例）を置く（WP-C5）。

## 7. Wasm変換（#5、Phase D）

```text
Core IR -> CFG正規化/構造化 -> register->local/stack 低下 -> Wasm命令対応 -> module出力
```

- 構造化制御フロー: 任意のCFGを`block`/`loop`/`br`へ変換する。既約CFGなら標準アルゴリズム（Relooper / Stackifier系）、既約でない場合は`loop`+ディスパッチ変数（状態変数による一般化）にfall backする。出力は決定的であること。
- レジスタ: r0〜r31を`i64` localにする。`r0`は定数0。
- guest memory: Wasm linear memoryの先頭`memory_bytes`にmapし、メモリ範囲検査を命令列で明示（Wasmのtrapを使う場合も、Coreの`memory_out_of_range`への対応をruntimeで定義）。
- trap: Core trapを`unreachable`＋hostのtrap通知、または戻り値で表す。方式は設計PR（D1着手時）で固定し、観測JSONに写像できること。
- `jal`/`jr`: indexのテーブルによる間接ジャンプ（`br_table`）で表す。
- 単純な算術・比較はJSON mapping基盤を再利用可。Wasm専用のCore命令は追加しない。
- 完了条件: 代表Core programが妥当なWasm moduleに変換され、観測結果が参照VMと一致し、変換が決定的（#5）。

## 8. JVM bytecode変換（#6、Phase D）

```text
Core IR -> CFG正規化 -> register->local lowering -> verifier/type-state 適応 -> JVM命令対応 -> class/method出力
```

- レジスタ: `long` local。operand stackはJVM側の一時用。
- guest memory: JVM objectを生アドレスにしない（DEC-15）。guest memoryは`byte[]`（または`ByteBuffer`/`MemorySegment`）を明示runtime表現にし、範囲検査はruntime helperで行う。
- 分岐/jal/jr: labelへ`goto`/`if*`。`jr`は`tableswitch`/`lookupswitch`で目的indexへ。ネストしたmethod境界は使わず、単一method（巨大化する場合はCFGを分割しframe状態を明示）。
- verifier: スタックmap frameを決定的に生成する（手書きまたは`ClassWriter`相当を自前実装。外部依存を増やさない方針）。
- trap: Java例外を使う場合も、観測JSONへ写像する規則を固定（例外種別→trap kind）。
- 完了条件: 代表Core programが検証器を通るclassfileになり、JVM上の観測結果が参照VMと一致し、出力が決定的（#6）。

## 9. 受け入れ条件

- WP-C1: schema v2・loader・expander・encoder境界インターフェース、単体テスト。
- WP-C2: 三ターゲットのv1表（L1/L2/L3まで）。
- WP-C3: v1命令の網羅CI（未網羅の通常opcodeでCIが失敗）。
- WP-C4: L4実行等価（環境が使える範囲）。未達の場合は理由とともに明記。
- WP-C5: 独自ターゲット例とドキュメント。
