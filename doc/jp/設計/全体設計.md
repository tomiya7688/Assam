# 全体設計

言語: 日本語 | [English](../../en/design/overview.md)

状態: 設計正本（Issue #1〜#6, #10, #13〜#15, #28, #29 を統合）。個別の決定は[決定ログ](決定ログ.md)を参照する。

## 1. 目的と位置づけ

ASSAMは、人間向けの便宜機能を持つ**Full ASSAM**と、機械が生成・処理する厳密な低水準部分集合**Assam Core**からなる。Coreは次の連鎖の共通境界になる。

```text
Bitlang Low
    -> Bitlang VM Backend
    -> Assam Core（canonical text / JSON IR）
    -> Bitlang VM（Go, 主実行系）
    -> x64 / ARM64 / RISC-V 変換（JSON対応表）
    -> （後続）Wasm / JVM bytecode 変換
```

Assamは次を提供する。

1. Coreの**文法・意味論・版契約**（正本は文書とregistry/schema）
2. 参照実装（Python parser / VM / analyzer / CLI）
3. 機械可読な**命令registry**と、それを使う検証・変換・conformance基盤
4. 宣言的な**ターゲット対応表**の検証基盤と同梱Draft/正式表

## 2. 設計原則

1. **正本は一つ**: opcode・operand・効果・trap・版は registry/schema。実装言語ごとの複製を禁止する（DEC-10）。
2. **Coreは小さく**: 新opcodeは3ターゲットへ宣言的に対応でき、効果とtrapが明示できることを要する。ホストや特定CPUの都合だけで追加しない。
3. **Fail-closed**: 不正・曖昧な入力は実行前に診断して拒否する。黙った補正・近似・暗黙停止をしない。
4. **ホスト非依存**: Pythonの無限精度整数、JavaのObject参照、Rustのpanic等をguest意味論へ漏らさない。
5. **FullとCoreを混ぜない**: 互換aliasや高級命令はFullに限る。Core検証結果に混入させない。
6. **観測で比較**: 実装の正しさは、共通のconformance corpusに対する観測結果（レジスタ・メモリ・trap）の一致で判定する。
7. **検証できないことは主張しない**: 構造検査（網羅宣言・参照整合）と意味の等価性は別。後者が未検証なら完了と書かない。

## 3. Profile体系

| profile | 版      | 状態             | 説明                                                                                            |
| ------- | ------- | ---------------- | ----------------------------------------------------------------------------------------------- |
| `full`  | 現行    | 維持             | PascalCase・case-insensitive・空白区切り・r0〜r15・Push/Pop・端末命令。後方互換を維持           |
| `core`  | `draft` | **廃止予定**     | 現行のDraft。r0〜r15、無限精度整数、隠れたcall stack、疎memory。Core v1完了時に廃止（Q4）       |
| `core`  | `1`     | **新規実装対象** | Bitlang VM Core v1 consumer contract。[文法](Core文法とprofile契約.md)・[意味論](Core意味論.md) |

JSON IRのprofile印（`{"name","version","registry_schema_version"}`）は継続し、`core`/`1`を表現できるようにする（registry schema v3、[レジストリ](レジストリとconformance.md)）。印のない従来JSONは`full`のまま。

## 4. 現状と目標のギャップ

| 項目        | 現行（main）                           | 目標（Core v1）                                                  | 担当WP    |
| ----------- | -------------------------------------- | ---------------------------------------------------------------- | --------- |
| 構文        | PascalCase・空白/カンマ混在・aliasあり | 小文字・カンマ必須・aliasなし                                    | WP-B2     |
| operand表現 | 文字列が数値/レジスタに化ける（#10）   | register/immediate/symbolを型で区別。IRで保持                    | WP-B1     |
| レジスタ    | r0〜r15、通常レジスタ                  | r0〜r31、64bit、r0=0                                             | WP-B4     |
| 整数        | Python無限精度、幅・符号未決           | modulo 2^64、符号付き/なし命令を区別                             | WP-B4     |
| メモリ      | 疎、未書込read=0、幅なし               | 連続byte空間、幅明示、LE、範囲外trap                             | WP-B4     |
| 呼出        | 隠れたcall stack                       | link register（jal/jr）                                          | WP-B4     |
| trap        | `VMError`文字列                        | 安定した分類・位置・code                                         | WP-B4     |
| registry    | schema v2、幅/符号は`not_decided`      | schema v3、v1の全命令を機械可読で定義                            | WP-B3     |
| 変換        | Draft表（構造のみ検査）                | v1命令の3ターゲット表+fixture+実行等価                           | WP-C1〜C4 |
| CI          | pytest・ruff・pip検査・対応表検査      | +package smoke・CLI smoke・malformed corpus・conformance・schema | WP-A2     |
| 配布        | 未署名                                 | 成果物のdigest+attestation                                       | WP-A3     |

## 5. コンポーネント構成

```text
assam/
  parser.py          Full互換parserとCore canonical parser（分離）
  ir.py              Program / Instruction / 型付きOperand（B1で拡張）
  instruction_set.py registry読込み・profile別検証
  profile.py         profile識別子・IR印
  vm.py              Full VM / Core v1 VM（別クラス・別ファイル）
  analyzer.py        静的解析
  c_frontend.py      C部分集合 -> Core v1 canonical
  target_coverage.py 網羅宣言・対応表検査
  translator/        （C1以降）loader・template expander・encoder境界
  data/              registry・各種schema（正本）
examples/
  conformance/       共有conformance corpus
  targets/           同梱対応表
```

1クラス1ファイル・1責務のルールに従う。VMはFullとCore v1で意味論が異なるため**別クラス**にし、共通部分は継承ではなく委譲・合成で共有する（[コーディングルール](../コーディングルール.md)の継承規約）。

## 6. 実装言語の役割（DEC-14）

| 言語   | 役割                                                                | 状態                                       |
| ------ | ------------------------------------------------------------------- | ------------------------------------------ |
| Go     | 主実行系（Bitlang VM）。将来のセルフホストまでのbootstrap/reference | 別リポジトリ。Assamのregistry/corpusを利用 |
| Python | parser・参照VM・conformance基準・検査ツール                         | 本リポジトリ                               |
| Java   | 独立したJava製VM（#14）。JVM bytecode変換（#6）とは別               | 将来。[追加実行系](追加実行系.md)          |
| Rust   | 安全性重視のネイティブVM候補（#15）                                 | 将来。同上                                 |

いずれも「完全な安全性を自動保証するもの」ではなく、FFI/ネイティブ拡張/実装バグは別途検証対象とする。

## 7. フェーズと依存

```text
Phase A  基盤:    A1 pip/certifi(#28) -- A2 CIゲート(#13) -- A3 署名/attestation(#29)
Phase B  契約:    B1 operand型(#10) -> B3 registry v3(#2) -> B2 Core文法(#1) -> B5 conformance -> B4 意味論+VM(#3) -> B6 移行
Phase C  変換:    C1 mapping schema v2/loader(#4) -> C2 3ターゲット表 -> C3 網羅CI -> C4 変換実行等価 -> C5 独自ターゲット
Phase D  将来:    D1 Wasm(#5), D2 JVM(#6), D3 Java VM(#14), D4 Rust VM(#15)
```

詳細な作業単位・依存・受け入れ条件は[実装計画](実装計画.md)。Phase Aは機能開発より優先する（#28・#29はP0）。Phase DはPhase B完了（契約+conformance+CI）とPhase C（3ターゲット安定）を前提にする。

## 8. 非目標

- Coreへの高級命令（string処理・端末・allocation・closure・ownership）の追加
- BitlangのMIR/ownership/borrow等の再解析（変換器もCoreもしない）
- JSON対応表への汎用プログラミング言語の埋め込み
- 実行ロジックのJSON化（registryは命令契約と対応情報のみ）
- x*（任意精度）・Floatの1命令化（x*は明示lowering、Floatはv1対象外）
- Java/Rust VMのために仕様を変えること

## 9. リスクと対策

| リスク                                                 | 対策                                                                                 |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Draft→v1で既存テスト・C frontendが壊れる               | FullとCore v1を別実装にし、C frontendの出力切替は独立したWPにする                    |
| 実装間の意味論drift                                    | conformance corpusを唯一の比較基準にし、registry変更時に全corpus実行をCI必須にする   |
| 対応表が構造のみ検査で意味が未検証のまま完了扱いされる | 検査スコープ名（`validation_scope`）を報告に必ず含め、C4（実行等価）を完了条件に分離 |
| 設計と実装の乖離                                       | 乖離は設計PRで先に直す。各WPに「設計参照」と「Definition of Ready」を置く            |
| P0供給網課題が機能開発に埋もれる                       | Phase Aを先頭に固定し、A1〜A3未完でリリースしない                                    |
