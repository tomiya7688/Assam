# 実装計画

言語: 日本語 | [English](../../en/design/implementation-plan.md)

設計正本（[全体設計](全体設計.md)ほか）を、1作業単位=1ブランチ=1PR=1機能に分割する。担当者（人間・AI）は**自分のWPの行とリンク先の節だけ**を読めば実装に入れる。

## 1. 共通ルール

**着手前（Definition of Ready）**

1. [ワークフロー](../ワークフロー/ワークフロー.md)の手順で`git fetch`/`pull --rebase`済み。
2. 対象WPの「前提」が`main`に入っている。未了なら着手しない。
3. 「ブロック」欄の未決事項（[決定ログ](決定ログ.md)）が確定済み。未決なら先に決める。
4. 「設計参照」を読み、受け入れ条件が実装・テストに落とせると確認した。設計が足りない・矛盾する場合は**実装を始めず、設計PRで先に直す**。

**完了（Definition of Done）**

1. 受け入れ条件の各項に対応するテストがある（テスト名または`tests`のパスをPRに書く）。
2. 該当文書（仕様・registry説明・roadmap・日英両方）を同じPRで更新。
3. CI成功、セルフレビュー済み、未検証事項は「未検証」と明記。
4. 作業中に分かった設計の不備は決定ログ/設計書へ反映（コードだけを直して済ませない）。

**PRの大きさ**: 1PRは1WP（大きいWPはa/bに分割）。無関係な整形・リネームを混ぜない。

**担当の目安**（Issueのagent-routing注記に従う）: 文法・意味論・ISA・変換表の設計判断を含むWPは上位担当（設計判断と検証を主導）。仕様が確定した定型実装（テスト追加、ドキュメント整備、単純な移植）は軽量担当へ分担可。完了判定は上位担当が行う。

## 4. 手戻りを防ぐ運用ルール

1. 判断に迷ったら[決定ログ](決定ログ.md)→設計書→Issueの順に読む。決定ログにない判断はPRに「判断メモ」として残し、必要なら決定ログを更新する。
2. 設計と実装が矛盾したら、実装を直す前に設計を直すPRを出す（人間がレビュー）。
3. 一つのPRでregistry・IR・VM・変換表の複数を同時に変えない。契約（registry/schema）→パーサ→VM→変換の順に、前提を`main`に入れてから次へ進む。
4. 互換契約（trap kind、診断code、registry `id`、観測JSON、IR schema）の変更は設計PR→実装PRの順。
5. 完了報告には検査の階層（L1〜L4、構造/意味）と未検証を必ず書く。
