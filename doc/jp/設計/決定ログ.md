# 設計決定ログ

言語: 日本語 | [English](../../en/design/decision-log.md)

実装者が設計を再解釈して手戻りしないよう、決定を一箇所に集める。実装中に判断が必要になったら、ここを先に読む。ここと矛盾する実装をしない。矛盾が必要なら**先にこの文書を直す設計PR**を出す（[ワークフロー](../ワークフロー/ワークフロー.md)）。

区分:

- **確定**: Issueに明記された、またはユーザーが決めた事項。変更にはIssue上の合意が要る。
- **提案**: Issueが未規定の部分を、本設計が決めた事項。実装はこれに従ってよい。レビューで覆す場合は設計PRで更新する。
- **未決**: 決まっていない事項。該当する実装単位は着手前に決定する。「ブロック」欄が空でなければ、その作業単位はこの決定を待つ。

## 提案（本設計が決める）

| ID     | 提案                                                                                                                                                                                                   | 理由                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| PRO-01 | profile識別子: 名前`core`、版`1`。現行`draft`は`1`の実装完了時に廃止し、Fullとは別系統の版として管理する                                                                                               | #3「Core profile versionで意味を分ける」                                                                                  |
| PRO-02 | Core v1のALU命令はレジスタoperandのみ。即値は`const`で入れる（`add rd, rs1, rs2`）。load/storeだけ符号付きオフセット即値を持つ                                                                         | issue例（`const`と`sub r1, r1, r2`）に一致。対応表のoperand種別を減らし、ターゲット側の即値制限を`const`1箇所に閉じ込める |
| PRO-03 | 符号付き`MIN / -1`は`MIN`（折返し）、剰余は`0`でtrapしない。除数0は`div_by_zero` trap                                                                                                                  | RISC-V既定動作と一致させ、他ターゲット側は対応表で補う。「結果を規定する」要求を満たす                                    |
| PRO-04 | opcode表は[Core意味論](Core意味論.md)の一覧とする                                                                                                                                                      | #3の必須領域を過不足なく満たす最小集合                                                                                    |
| PRO-05 | instruction indexは0始まり。`jal`が書く値は「次の命令のindex」。`jr`の対象が`[0, 命令数)`の範囲外（末尾の次を含む）なら`invalid_jump_target` trap。命令列の末尾を越えて暗黙停止しない                  | fail-closed。静的に分かるlabelの範囲外はload時に拒否                                                                      |
| PRO-06 | trap分類は固定列挙（`div_by_zero` / `memory_out_of_range` / `invalid_jump_target` / `unknown_helper` / `explicit`）。`explicit`は32bit符号なしの利用者codeを持つ。ステップ上限は環境制限でありtrapと別 | #3「安定したtrap分類と位置」。Python VMの現行`VMError`との橋渡しを明確にする                                              |
| PRO-07 | 実行結果の観測可能な形は`{status: halted                                                                                                                                                               | trapped, trap?: {kind, code?, pc}, registers[32], memory(sha256またはdiff)}`の共通JSONとする                              | 複数VMの比較（conformance）に必要 |
| PRO-08 | memoryは実行インスタンスのパラメータ`memory_bytes`（既定1 MiB）で与え、ゼロ初期化の連続領域とする。疎なmemoryの未書き込みread=0はFullのみ維持                                                          | #3「疎memoryの未書込read=0は契約と不一致」の解消                                                                          |
| PRO-09 | Core v1 programの初期memory内容はJSON IRの`memory.segments`（`{offset, bytes}`）で与える。canonical textはdata directiveを持たない（`const`+`st*`で初期化可能）                                        | Q2の暫定。text文法を増やさず、必要ならQ2で拡張                                                                            |
| PRO-10 | 変換表schema v2は条件・幅variant・scratch・ABI helperを宣言的に持つ（[ターゲット変換](ターゲット変換.md)）                                                                                             | #4                                                                                                                        |
| PRO-11 | conformance corpusは`examples/conformance/`にJSONケース+期待観測結果で置き、全VM・変換結果が同一ファイルを読む                                                                                         | #8, #13, #14, #15                                                                                                         |
| PRO-12 | 実装は[実装計画](実装計画.md)の作業単位WP-xxに分け、1作業単位=1PR=1機能で進める                                                                                                                        | 手戻り防止                                                                                                                |
| PRO-13 | 各命令は「trap判定→副作用のcommit」の順。`st*`は範囲全体を先に検査して部分書込みしない。`hcall`未登録idは副作用なしtrap。`jal`が最終命令で書く`命令数`は無効indexで`jr`するとtrap                      | レビュー指摘（Luna, Antigravity）。実装間の観測差を防ぐ                                                                   |
| PRO-14 | `memory.segments`の範囲外・重複は実行前に`core.load.*`診断で拒否。スタック領域・SP・呼出規約・レジスタ保存規約はCoreの外（Bitlang backendの責務）                                                      | 同上。Coreを小さく保つ（DEC-14の原則）                                                                                    |
| PRO-15 | `divs`の商は0方向丸め、`rems = a - divs(a,b)*b`（剰余の符号は被除数）。即値の範囲は命令ごとに固定（`const`は`[-2^63, 2^64-1]`ほか）                                                                    | 同上。3ターゲットで同一結果を得るため                                                                                     |

## 未決

| ID  | 論点                                                       | 推奨                                                                                                                    | ブロック             |
| --- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Q1  | 64bit上位乗算（`mulhu`/`mulhs`）をv1 Coreに含めるか        | 含める。含めない場合、x\*乗算は剰余分割のruntime helperになりBitlang側の負担が増える。3ターゲットとも1〜2命令で対応可能 | WP-B4, WP-C1         |
| Q2  | 初期データ・グローバルの表現（PRO-09の暫定で十分か）       | IR `memory.segments`で開始し、Bitlang backendの要求が出た時点で再検討                                                   | なし（暫定で進行可） |
| Q3  | `memory_bytes`の既定値と上限                               | 既定1 MiB、上限は実装定義だがtrapで報告                                                                                 | なし                 |
| Q4  | Draft Core（PascalCase）で書かれた既存プログラムの移行方針 | Draft CoreはExamples以外に利用者がいないため、v1完了時に廃止。FullのPascalCaseは維持。C frontendの出力をv1に切替        | WP-B4                |
| Q5  | `Float<Radix>x*`・浮動小数点                               | v1 Coreでは扱わない。Bitlang側の定義後に別Issue                                                                         | なし                 |
| Q6  | 入出力・端末（`syscall`相当）                              | Coreに入れない。Full端末命令のまま、必要ならBitlang VMのhost境界で扱う                                                  | なし                 |
| Q7  | 実行系間で差が出うる「ステップ上限」の標準値               | conformanceでは実装ごとの上限に依存しないケースだけ作る                                                                 | なし                 |

ブロックのある未決（Q1, Q4）は、該当作業単位の**着手前**にユーザーまたはBitlang担当が決める。決まったら確定表へ移し、関連設計書を同じPRで更新する。
