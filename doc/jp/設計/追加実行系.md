# 追加実行系（Java VM / Rust VM）

言語: 日本語 | [English](../../en/design/additional-runtimes.md)

対象Issue: #14（Java VM）、#15（Rust VM）、#2（実装言語の役割）。決定: DEC-14, DEC-16。状態: Future（Phase D）。

## 1. 位置づけ

| 実装               | 役割                                                 | 比較基準           |
| ------------------ | ---------------------------------------------------- | ------------------ |
| Go（Bitlang VM）   | 主実行系                                             | conformance corpus |
| Python（ASSAM VM） | 参照実装・基準                                       | conformance corpus |
| Java VM（#14）     | 独立した追加実行系。Core programをJava上で解釈・実行 | 同上               |
| Rust VM（#15）     | 安全性重視のネイティブ追加実行系                     | 同上               |

- 追加実行系は**Go主実行系の置換ではなく互換実装の追加**。仕様の正本は言語VMではなくschema/registryと[Core意味論](Core意味論.md)。
- Java VM（#14）は **JVM bytecode変換（#6）とは別物**。前者はCore programの解釈実行、後者はCoreからclassfileへの変換。
- 実行ホストのクロスプラットフォーム性と、Core→x64/ARM64/RISC-V変換（#4）は別課題で、両方を維持する。

## 2. 着手条件（Definition of Ready）

次がすべて満たされるまで着手しない（重複実装と仕様driftを避ける）。

1. Core v1の文法・意味論・registry v3が確定し、Python参照実装が準拠している（WP-B1〜B4完了）。
2. 共有conformance corpusと実行系プロトコル（`<impl> conformance-case`）が整備されている（WP-B5）。
3. CI（#13）がconformance必須で、参照実装で全件通る。
4. 三ターゲット変換（#4）が安定している（WP-C3まで）。ただしJava/Rust VMの整備は必須ターゲットgateの代替にならない。

## 3. 共通設計制約

- **registry/schemaを実装側で複製しない**。registry JSONを読み込む、または生成物を使い、sha256を固定する。
- **ホスト固有の意味を採用しない**: Javaの数値幅/例外/参照、Rustのoverflow/panic/pointerをguest意味論に出さない。算術は明示的にwrapする（Rust: `wrapping_*`、Java: `long`のwrap＋符号なし演算の`Long.divideUnsigned`/`Math.multiplyHigh`等）。
- **fail-closed**: 未知命令・不正operand・不整合profileは実行前に拒否。
- **新しい高級Core命令を追加しない**。
- 入出力は`conformance-case`プロトコルと、最小CLI（`run`, `check`）、実行API（ライブラリ）。

## 4. Java VM（#14）

- 配置: 別リポジトリ（またはこのリポジトリの`runtimes/java/`。決定は着手時に設計PR）。Javaバージョンは最小LTS（着手時に確定）。
- 構成: `Loader`（text/IR）→`Validator`(registry)→`Machine`（`long[32]`、`byte[] memory`、`pc`）→`Observation`。
- 数値: レジスタは`long`。符号なし比較・除算・剰余・上位乗算は`Long.compareUnsigned`/`divideUnsigned`/`remainderUnsigned`/`Math.unsignedMultiplyHigh`（Java 18+）。
- メモリ: `byte[]`の範囲検査を自前で行い、`ArrayIndexOutOfBoundsException`をguest trapとして漏らさない。
- 完了条件（#14）: 同一version・同一programでGo・Python・Javaの観測結果が一致、Javaがconformance全件合格、Javaが独自の命令定義/意味論を持たない。

## 5. Rust VM（#15）

- 配置: 別リポジトリ（または`runtimes/rust/`）。safe Rustを原則とし、`unsafe`/FFIは境界と必要性を文書化して監査する。依存は最小（serde系は許容、理由を記録）。
- 構成: `registry`（生成またはJSON読込）、`parser`、`program`、`machine`、`observe`。
- 数値: `u64`と`wrapping_*`/`overflowing_*`、`i64`は`as`で符号解釈。`panic`をguest動作にしない（`catch_unwind`で拾うのではなく、panicが起きない設計を第一にし、起きたらhost error）。
- クロスプラットフォーム: Windows/Linux/macOS × x64/ARM64でbuild+conformanceをCIで実行。
- 完了条件（#15）: 共有corpusを実行でき、代表programの結果・trap・診断が既存VMと一致。

## 6. 受け入れ条件

- WP-D3（Java）/ WP-D4（Rust）は、それぞれ上記着手条件の充足を最初にPRで確認する。
- 実装完了の判定は**conformance全件合格**と**差分テスト（Go/Python/本実装）の一致**。外部ツールが使えず未実施の項目は明記する。
