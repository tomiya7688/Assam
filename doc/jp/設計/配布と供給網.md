## 1. Assamが配布する成果物の棚卸し（#29「成果物の種類を列挙」）

| 成果物                                     | 生成                            | 現状       | 方針                                                                                               |
| ------------------------------------------ | ------------------------------- | ---------- | -------------------------------------------------------------------------------------------------- |
| Python wheel (`assam-*.whl`)               | `python -m build`               | 未リリース | digest + attestation（Sigstore）                                                                   |
| sdist (`assam-*.tar.gz`)                   | 同上                            | 未リリース | 同上                                                                                               |
| conformance corpus / registry の配布物     | tag時のtar.gz（Go等が取り込む） | 未         | 同上＋sha256を文書に記載                                                                           |
| GitHub Release asset                       | リリースworkflow                | 未リリース | 上記すべてをassetにし、`SHA256SUMS`と検証手順を付与                                                |
| 実行ファイル / installer / APK / container | なし                            | 該当なし   | **現時点で該当なし**。将来追加する場合はIssue #29の該当節（Windows/macOS/Android/container）に従う |

「現時点で該当なし」の項目は、完了条件で「未使用確認済み」として扱う（#29「該当する場合」）。

## 2. リリース成果物の署名・attestation（WP-A3）

- `release` workflowはタグ（`v*`）で起動し、**GitHub Actions + OIDC**でkeylessにする。秘密鍵・PFX・keystoreは使わずコミットしない。
- 手順: build（wheel/sdist）→`SHA256SUMS`生成→`actions/attest-build-provenance`でそれぞれにattestation→`SHA256SUMS`自体もattestation→Release assetへ添付。
- 検証をCI/リリースgateに入れる: リリース直前に`gh attestation verify`（またはcosign）で生成直後の成果物を検証し、失敗したらreleaseしない。
- ユーザー向け検証手順をREADMEとRelease notesに書く:
  ```text
  gh attestation verify assam-X.Y.Z-py3-none-any.whl --repo tomiya7688/Assam
  sha256sum -c SHA256SUMS
  ```
- PyPI等に公開する場合は、Trusted Publisher（OIDC）とPEP 740 attestationを使う（公開する決定をしたときに別WP）。
- 既存成果物: 現時点でリリース済み成果物は存在しない（確認はA3の最初に`gh release list`で記録する）。再現不能な古い成果物があれば「未署名・検証不可」と明示する。

完了条件: 成果物種類の列挙、各成果物のdigest+attestation、CIでの検証成功、秘密情報がリポジトリに無いこと、検証手順の文書化、既存成果物の状況確認（#29）。

## 3. Python証明書インシデント対応（WP-A1、#28）

要求（#28）: `pip >= 26.2.2`、`certifi >= 2026.10.19`、使用している場合は`uv >= 0.13.4`・`sigstore >= 4.5.1`。更新コマンドだけで完了とせず、**実際に信頼しているCA bundle**を確認する。

Assamの調査対象と方針:

| 対象                                         | 方針                                                                                                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| CI (GitHub Actions)                          | pipをSHA-256固定のwheelでブートストラップ（導入済み）。pip同梱CA bundleを検査するステップ（導入済み、`tools/check_pip_ca_bundle.py`）。結果をPRに記録 |
| 開発者のローカルvenv                         | 手順書に確認コマンドを記載し、`python -m pip --version`・`certifi.__version__`・`certifi.where()`を記録                                               |
| 依存宣言                                     | `pyproject.toml`の`dev` extraに古い固定がないこと。`uv`/`sigstore`は**現時点で未使用**（#29の導入時に最小要件を固定）                                 |
| 配布物内のCA bundle                          | wheelは純Pythonでcertifiを同梱しない。確認結果を記録                                                                                                  |
| 問題の証明書チェーンが信頼されないことの確認 | Issue #28に従い、実際のCA bundleで該当チェーンが検証失敗になることをスクリプトで確認（`tools/check_pip_ca_bundle.py`の拡張）                          |

確認結果には、確認したPython/venv/成果物、参照したCA bundleまたはtrust store、確認時のversionを残す。この作業は別ブランチ（`fix/issue-28-*`）で進行しており、本設計はその完了条件を整理するだけで、重複して着手しない。
